# Development Plan

## 1. 开发节奏

后续开发按阶段推进。每个阶段必须满足三个条件才算完成：

1. 代码已实现。
2. `npm run build` 通过。
3. 在真实 vault 中同步并完成一次手动验证。

原则：

- 每次只做一个阶段。
- 不在同一阶段混入无关 UI 重构。
- 每个阶段结束后更新本文档状态。
- 能先用清楚交互解决的问题，不先做复杂架构。

## 3. Phase 1：封面设置交互

目标：让用户不需要理解 `cover` 字段，也能明确选择公众号封面。

范围：

- 新增封面来源选择：
  - 使用正文第一张图
  - 使用指定图片
  - 使用已有微信素材 media_id
- 展示当前笔记检测到的图片缩略图。
- 保存指定图片到 `cover`。
- 保存已有素材到 `cover_media_id`。
- 发布逻辑按封面来源解析。
- 发布检查中明确说明当前封面来源。

验收标准：

- 正文有图片时，默认可以直接发布。
- 用户能从图片列表点选封面。
- 用户能填写 media_id 并发布。
- 切换封面来源不会留下冲突 frontmatter。
- `npm run build` 通过。

不做：

- 封面裁剪。
- 上传前压缩。
- 微信素材库浏览。
- AI 生成封面。

状态：已实现，待 Obsidian 手动验证。

## 4. Phase 2：发布检查可操作化

目标：检查区不只展示问题，还能帮助用户直接处理问题。

范围：

- 检查项支持 action 按钮。
- 封面缺失时提供：
  - 选择正文图片
  - 填写 media_id
- 微信连接异常时提供：
  - 复制当前公网 IP
  - 打开微信后台基本配置页
  - 测试连接
- 摘要为空时提供：
  - 使用正文首段
- 草稿有更新时提供：
  - 更新草稿

验收标准：

- 至少 3 类高频问题可以从检查项直接处理。
- 阻塞错误不会只给文字说明。
- 操作后检查区立即刷新。

不做：

- 自动登录微信后台。
- 自动配置 IP 白名单。

状态：未开始。

## 5. Phase 3：设置页重组与连接诊断

目标：让首次配置更容易成功。

范围：

- 设置页分组：
  - 微信公众号
  - 默认发布信息
  - 高级
- AppSecret 保存状态更明确。
- 测试连接显示最近一次结果。
- 错误提示翻译为可理解文案。
- 增加“打开微信后台基本配置”链接。
- 增加“复制当前公网 IP”主操作。

验收标准：

- 新用户能按设置页提示完成连接配置。
- IP 白名单错误能被明确识别。
- AppSecret 不会被空输入覆盖。

不做：

- OAuth 授权。
- 云端代理服务。
- 多账号管理。

状态：未开始。

## 6. Phase 4：工作台布局整理

目标：把工作台从“功能堆叠”整理成稳定的发布控制台。

范围：

- 顶部状态栏重写。
- 工具栏按钮文案和状态重写。
- 发布信息、封面、检查、预览的视觉层级统一。
- 发布结果区固定位置。
- 移动宽度和窄侧栏下可用。

验收标准：

- 用户不用滚动太多就能理解当前文章状态。
- 主按钮始终符合当前草稿状态。
- 窄宽度下字段不挤压、不重叠。
- UI 与 Obsidian 原生风格一致。

不做：

- 大面积品牌视觉重设。
- 模仿 WeSight。
- 营销页式 hero。

状态：未开始。

## 7. Phase 5：复制 HTML 与发布路径区分

目标：避免用户误以为“复制 HTML”和“发布草稿”的图片处理完全一样。

范围：

- 复制 HTML 时显示图片处理提示。
- 发布路径继续上传图片到微信。
- 复制路径可选择：
  - 复制本地预览 HTML
  - 复制发布级清理 HTML
- HTML 审计结果展示更清晰。

验收标准：

- 用户知道复制 HTML 后图片可能需要手动处理。
- 发布路径不会因为本地 app:// 图片误报。
- HTML 兼容性检查不干扰正常预览。

状态：未开始。

## 8. Phase 6：发布稳定性

目标：降低真实发布失败率，提高失败后的恢复能力。

范围：

- access_token 缓存策略检查。
- 图片上传失败重试。
- 微信 API 错误码映射。
- 上传缓存清理入口。
- 发布过程日志。
- 诊断信息导出。

验收标准：

- 常见微信错误码有中文解释。
- 图片上传失败时能知道是哪张图片。
- 用户可以清除缓存后重试。
- 发布日志足够支持排查问题。

状态：未开始。

## 9. Phase 7：主题系统

目标：让主题扩展变得稳定，而不是在 renderer 中堆判断。

范围：

- 明确主题 API。
- 每个主题独立文件。
- 主题预览样例。
- 主题兼容性限制说明。
- 新增主题时不影响发布逻辑。

验收标准：

- 新增主题只需要新增主题文件并注册。
- 主题不能引入微信不兼容 HTML。
- 至少保留 4 个可用主题。

状态：部分完成。

## 10. Phase 8：外部测试与发布

目标：从“自己能用”走向“别人能装、能配置、能发布”。

范围：

- 找 1-2 个测试用户安装。
- 收集安装、配置、发布失败点。
- 更新 README 截图版安装说明。
- 发布 v0.2.0。
- 评估是否提交 Obsidian 社区插件市场。

验收标准：

- 外部用户能完成首篇草稿发布。
- README 能覆盖首次安装流程。
- release zip 和源码版本一致。

状态：未开始。

## 11. 每阶段完成清单

每次开发结束前检查：

- `npm run build` 通过。
- 插件文件已同步到真实 vault。
- 至少验证一个真实笔记。
- README 或 docs 已同步更新。
- 如要发布，运行 `npm run release`。
- 如要推 GitHub，提交、打 tag、创建 release。

## 12. 决策规则

遇到新想法时，先判断：

1. 是否影响“预览、检查、发布草稿”主流程？
2. 是否属于当前 phase？
3. 是否能用更小改动解决？
4. 是否会引入新的用户配置成本？
5. 是否会让微信 API 风险变高？

如果答案不清楚，先写进 backlog，不直接开发。
